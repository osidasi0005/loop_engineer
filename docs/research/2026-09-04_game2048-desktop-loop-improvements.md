## 1. 「確認だけの反復」を減らす

### 根拠

4 タスクすべてが「反復 1 で実装 → 反復 2 で完了条件を照合して宣言 → 反復 3 の検証で確定」だった。

| タスク | 反復 1 | 反復 2（宣言のみ） | 合計 |
|---|---|---|---|
| 03 view | $0.44 | $0.39 | $0.83 |
| 04 app | $1.12 | $0.24 | $1.36 |
| 05 build | $0.31 | $0.38 | $0.69 |
| 06 style | $0.89 | $0.35 | $1.24 |
| 計 | $2.76 | **$1.36（33%）** | $4.12 |

反復 2 のエージェントは、実装を変えず「テストを再実行し、完了条件を 1 つずつ確認し、マーカーを書く」だけだった。
今のルール（`buildPrompt` の `rulesFail`）は「直前の検証が FAIL なら完了マーカーを書くな」なので、
反復 1 で実装と自己検証が済んでいても宣言できない。

### 提案

- FAIL 起点の反復でも「検証コマンドを自分で実行して PASS し、完了条件をすべて確認した」場合はマーカーを書いてよい、に緩める
- ランナー側は変えない。マーカーがあっても次の反復の検証が PASS しなければ完了にしない、という 2 段構えはそのまま
- 安全性の根拠: 完了判定は常にランナーの検証結果で行う。エージェントの自己検証は「宣言してよいか」の条件に使うだけ
- 期待効果: 1 タスクあたり 1 反復（$0.25〜0.4）減。最短経路が 3 反復 → 2 反復（実装 → 検証で確定）

### 注意

- テストで検出できない完了条件（コメントの有無、対話操作の手順確認など）は、反復 1 の中で確認させることになる。
  仕様の「完了条件」を今までどおり明記しておけば、確認の場所が変わるだけで抜けは増えない
- モック（`examples/mock-agent.mjs`）は 3 反復の筋書きなので、緩和後は 2 反復で終わる筋書きに合わせる

## 2. 内側のエージェントに git を渡さない設定を既定にする

### 根拠

`.claude/settings.json`（プロジェクトの許可リスト）に `Bash(git commit *)` を許可した直後、
`claude -p` で起動された内側の Sonnet が自分で `git commit` した（コミット d83b46d 相当、
本文「反復 2 検証 PASS → 完了条件をすべて確認」）。`--allowedTools` で git を渡していなくても、
プロジェクト設定の allow が加算されて通る。

ランナーがコミットする設計（申し送りをコミット本文に残す、エージェントに「コミットしたから完了」と誤認させない）と衝突する。

### 提案

- `loop.mjs` がエージェントを起動するとき、常に `--disallowedTools "Bash(git:*),PowerShell(git:*)"` を付ける
  （設定で明示的に許可した場合だけ外す）
- `new-task.mjs` の雛形にも同じ指定を入れる
- README の「反復ごとに自動コミットする」の節に、プロジェクトの許可リストが内側にも効くことを書く

今回は `tasks/2048-03..06/loop.config.json` にだけ追加した。slugify、mazechase、textkit のタスクは未対応。

## 3. ランナーの git ロック衝突を扱う

### 根拠

改善ループ 06 の反復 1 で、人間（このセッション）が同じリポジトリでコミットしている最中にランナーの自動コミットが走り、
`[1] 自動コミット失敗: git commit 失敗: null` で終わった。ランナーは `git add -A` まで済ませていたので、
エージェントの差分（`style.css`、`probe.cjs`）がステージに残り、人間の次のコミット（許可リストの変更）に混ざった。
push 前に `git reset --soft` で分割し直した。

### 提案

- `commitIteration` で `.git/index.lock` を検知したら短い間隔で数回再試行する
- 失敗理由を `null` ではなく stderr の内容で出す（`runGit` の戻りの `stderr || error` を使う）
- 失敗したときはステージを戻す（`git reset -q`）か、少なくとも「ステージに残っている」と警告する
- README に「ループ実行中はそのリポジトリで git add / commit をしない」を明記

## 4. 見た目の検証をハーネスの仕組みにする

### 根拠

タスク 04 は「HTML の構造」「窓のサイズ」「タイル数」のテストをすべて通したが、実際に画面を撮ると
2〜16 のタイルが白ではなく墨で塗られていた。原因は CSS の詳細度（`.tile:not(.empty)` が `.v2` に勝つ）。
テストは「構造」を見ていて「見た目」を見ていなかった。

人間がスクリーンショットで気づき、計算済みスタイルと矩形を読むプローブ（`test/helpers/probe.cjs`）と
`test/style.test.mjs` を書いて改善ループ 06 で直した。プローブは検出器として残った。

### 提案

- `verify.artifacts`（例: `["shots/*.png"]`）を設定に持ち、検証コマンドが生成した画像を反復ごとの `runs/<日時>/` にコピーする。
  人間はループ終了後に画像を並べて見る。ループ自体の判定には使わない（画像の良し悪しは自動で判定しない）
- `test/helpers/probe.cjs` の方式（非表示ウィンドウで読み込み、`getComputedStyle` と `getBoundingClientRect` を JSON で吐く）を
  Electron 系タスクの雛形にする。色・寸法・重なり・はみ出し・スクロールの有無まで数値で照合できる
- 仕様を書く側の教訓として README に残す: UI の仕様は「クラス名」だけでなく「計算済みの色と寸法」で書き、
  テストもそこを見る

## 5. 仕様の穴の指摘を構造化して拾う

### 根拠

タスク 03 で、仕様に「won / over のときに `new` クラスを付けるか」を書き忘れていた。エージェントはテストの期待値から
正しい振る舞い（付けない）を読み取り、進捗メモの「分かったこと」に根拠を書いた。人間がたまたま読んで仕様を直したが、
進捗メモの中に埋もれると見落とす。textkit-fix の実験でも、エージェントは「仕様がテストと矛盾する根拠」を申し送りに書いていた。

### 提案

- エージェントへの指示に「仕様の抜け・矛盾を見つけたら `<spec-issue>…</spec-issue>` で囲んで書く」を加える
- ランナーは応答からそれを抜き出して `summary.json` と終了時の標準出力に列挙する
- wave ランナーの差し戻し判定（「仕様がテストと矛盾」で人に返す）とも同じ経路にできる

## 6. ループ前の環境準備を設定に持つ

### 根拠

エージェントはネットワーク禁止なので、`npm install`（Electron 本体約 120MB）、electron-builder のツール取得
（nsis、7zip）、Smart App Control の確認は人間が事前に済ませた。ループの途中で環境が変わった件
（Smart App Control が未署名 exe をブロックし始めた）も人間が対処した。これらは進捗メモにもコミットにも残らない。

### 提案

- `setup.command`（反復 1 の前に 1 回だけ実行。失敗したらループを始めない）を設定に持つ
- 実行結果を `runs/<日時>/setup.md` に残す
- 「ループで直せない失敗」（環境・権限・ネットワーク）を検証出力から見分けるのは難しいので、
  少なくとも同じ失敗が続いたときの警告文に「環境の問題なら人間が直す」を足す

## 7. 未実装時のスモークを即 FAIL にする

### 根拠

タスク 04 の反復 1 は `app/` が空の状態で検証が走り、Electron を起動するスモーク 3 本がそれぞれ 45 秒のタイムアウトまで
待った（検証 135 秒）。存在チェックを先に置けば数秒で FAIL になる。

### 提案

- スモーク系テストの先頭で `app/main.cjs` などの存在を `assert` してから起動する（テスト側の書き方の問題。雛形に反映）
- ランナー側では、検証のタイムアウトとは別に「前回と同じ失敗ハッシュなら検証をスキップする」ような最適化はしない
  （検証結果が真実、という原則を崩さない）
