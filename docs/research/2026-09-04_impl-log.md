# 実装ログ: claude-looper からの取り込み

[評価ノート](2026-09-04_claude-looper-evaluation.md) の「取り込む候補」を loop-harness に実装する過程の記録。
試したこと・失敗・判断の理由を時系列で残す。各節は原則 1 コミットに対応する。

## 取り込み順序と理由

| 順 | 項目 | 理由 |
|---|---|---|
| 1 | 反復ごとの自動コミット（申し送りをコミット本文へ） | 最も安く、2 の土台。エージェントへの指示を増やさずに済む |
| 2 | wave ランナー（worktree 並列 + ランナー側マージ検証） | 研究テーマ 1・2 の実験装置。claude-looper の最大の欠落をランナー側検証で埋める |
| 3 | new-task.mjs の PROMPT 雛形を Planner 形式へ | mazechase の PROMPT.md はすでにその粒度。雛形が追いついていないだけ |
| 4 | fix タスクと差し戻しの段階 | 2 が無いと意味を持たない |

## 1. 反復ごとの自動コミット

### 設計（着手前）

- 設定 `git.autoCommit`（既定 false）。CLI `--commit` / `--no-commit` で上書き
- コミットするのは **ランナー**。エージェントには何も足さない。エージェントに git を触らせると
  「コミットしたから完了」と誤認する余地が生まれるため
- タイミングは「エージェント実行 → ランナーが PROGRESS.md に 1 行追記」の直後。PROGRESS.md の状態と差分が一致する
- 対象は `targetDir` 配下と `progressFile`。両方が同じ git リポジトリ内にあることを起動時に確認し、
  リポジトリ外なら警告して無効化する（例題は loop-harness 自身のリポジトリ内なので有効になる）
- コミット本文 = PROGRESS.md のその反復のブロック（`### 反復 N` から次の見出しまで）。
  見つからなければ検証結果だけを書く。末尾に機械可読なトレーラー（Loop-Task / Loop-Iteration / Loop-Verify / Loop-Cost-Usd / Loop-Run）
- 差分が無ければコミットしない（完了確認だけの反復では PROGRESS.md しか変わらないが、それも記録に値するのでコミットする）
- git はシェル経由ではなく `spawnSync('git', args)` で呼ぶ。パスに空白があっても壊れないように

### 懸念

- 例題を自動コミットで回すと、loop-harness のリポジトリ履歴に試行コミットが積まれる。
  動作確認はスクラッチ領域に作った別の git リポジトリで行う
- Windows のパス比較（大文字小文字・区切り文字）。`git rev-parse --show-toplevel` の戻りは `/` 区切りなので正規化して比較する

### 実装

- `bin/loop.mjs` に `git` 節（`autoCommit` / `subjectPrefix`）、`--commit` / `--no-commit`、
  `detectRepo` / `extractProgressBlock` / `commitIteration` を追加。約 70 行
- タスク名は設定ファイルのあるフォルダ名から取る（`loop(slugify): 反復 2 …`）。`taskName` で上書き可
- コミットメッセージは `runs/<日時>/commit-NN.txt` にも残し、`iter-NN.md` の末尾に「## コミット」節を追記
- `new-task.mjs` の雛形に `git: { autoCommit: false }` を出す。README に節を追加

### 動作確認（モックエージェント、スクラッチの別リポジトリ）

| ケース | 結果 |
|---|---|
| git 管理下 + `autoCommit: true` | 反復 1〜3 で 3 コミット。反復 4 は完了判定のみでエージェント未起動、コミットなし |
| 反復 2 のコミット | `work/src/slugify.mjs` と `task/PROGRESS.md` の 2 ファイル。本文に「やったこと / 分かったこと / 次にやるべきこと」が入った |
| 反復 3 のコミット | `PROGRESS.md` のみ（完了条件の確認だけの反復）。設計どおり |
| git 管理外 + `--commit` | 「作業対象が git リポジトリ内ではありません」と警告して無効化、ループは通常どおり完走 |

### 気づき

- 本文に入るブロックは「`### 反復 N` から次の `###` まで」なので、ランナーが追記する `- [ランナー] 反復 N: …` の行も含まれる。
  検証結果とコストが本文に残るので、これはむしろ好都合。取り除かないことにした
- Windows で `git rev-parse --show-toplevel` は `/` 区切り・大文字ドライブ文字で返る。`resolve` した `\` 区切りパスと比較するため
  正規化関数を挟んだ。想定どおり一度で通った
- 1 回目の実装で両ケースとも期待どおりに動いたため、この節に「失敗」は無い。次の wave ランナーでは
  worktree とマージが絡むので、そこで試行錯誤が増える見込み
- claude-looper との違いを一言で言うと、向こうは **エージェントに** 申し送りを書かせ、こちらは **ランナーが** 進捗メモから
  機械的に取り出す。エージェントへの指示を増やさずに同じ情報が得られる
- 回帰確認で `npm run reset:example` を使ったところ、git 管理下の `examples/slugify/src/slugify.mjs` を削除し
  `tasks/slugify/PROGRESS.md` を初期化するため、作業ツリーに無関係な差分が出た。既存の挙動だが、
  自動コミットと組み合わせると「リセット差分」がコミットに混ざりうる。wave ランナーではリセットを
  git 操作（`git checkout -- <targetDir>` など）に置き換える方が筋が良い。今回は `git checkout --` で戻して対処

## 2. wave ランナー（worktree 並列 + ランナー側マージ検証）

### 設計（着手前）

claude-looper の Milestone × Wave のうち Wave だけを取り込む。Milestone（直列の機能単位）は今の「タスクを順に回す」で足りる。

**役割分担**: 判断はすべてランナー。エージェントは各 worktree の中で従来どおり `loop.mjs` として動くだけで、
git もマージも知らない。claude-looper で Verifier エージェントがやっていた「マージ → 検証 → done 判定」を機械処理に置き換える。

**構成**

- `tasks/<wave名>/wave.config.json` に Wave の列を書く。各 Wave は既存タスク（`tasks/<id>/loop.config.json`）の ID の配列
- `loop.mjs` に `--worktree <path>` を追加。作業対象を含むリポジトリのトップレベルを `<path>` に差し替え、
  `targetDir` と `progressFile` を worktree 内の同じ相対位置へ写す。`runsDir` は写さない（worktree を消してもログを残す）
- `loop.mjs` に `--run-dir <path>` を追加。wave 側がログの置き場を指定し、終了後に `summary.json` を読む

**1 Wave の流れ**

1. Wave の未完了タスクごとに `git worktree add -b loop/<id> <dir> HEAD`。並列数は `maxParallel` で制限
2. 各 worktree で `loop.mjs --task <id> --worktree <dir> --run-dir <…> --commit` を並列起動
3. 全部終わったら **完了（exit 0）したタスクだけ** を 1 つずつ現在のブランチにマージ。衝突したら `merge --abort` して未完了扱い
4. 未完了タスクは worktree の `PROGRESS.md` だけを現在のブランチに取り込む（**コードは捨てて記憶だけ残す**）。
   claude-looper はコードも記憶も捨てて HEAD からやり直す。ここが差になる
5. マージ後に Wave 全体の検証コマンド（統合テスト）を実行。FAIL なら停止（fix タスクの段階は項目 4 で足す）
6. 未完了タスクが残っていれば次ラウンド（`maxRounds` まで）、無ければ次の Wave

**停止条件**: 全 Wave 完了 / ラウンド上限 / 累計コスト上限（各タスクの summary.json を合算）/ 統合検証 FAIL / マージ対象なしのラウンドが続く

**題材**: `examples/textkit`。契約（定数）→ 独立モジュール 3 つ（slugify / wordCount / truncate）→ 統合（index）の 3 Wave 5 タスク。
モックエージェント `mock-agent-textkit.mjs` で回す。wordCount は 1 回目をわざと間違えて worktree 内の反復を見せる。
`MOCK_CONFLICT=1` で 2 タスクが同じファイルに別内容を書き、衝突 → 次ラウンドで再実行、の経路を通す

### 懸念

- worktree 内で `PROGRESS.md` に書かれた内容は、マージされないと消える → 上記 4 で救う
- 現在のブランチにマージするので、作業ツリーがクリーンでないと事故る。起動時に `git status --porcelain` が空であることを要求
- Windows で worktree のパスが長くなる。`runs/<wave>/<日時>/wt/<id>` に置く

### 実装と試行 1 回目（失敗）

`bin/wave.mjs`（約 340 行）、`loop.mjs` の `--worktree` / `--run-dir`、`examples/textkit`、`mock-agent-textkit.mjs`、タスク 5 つを作成して
モックで実行。**Wave 1 の直後に停止した。**

```
[wave] textkit  ブランチ=claude/…  並列4  ラウンド上限3  予算$10
  textkit-01-contract: complete  反復3回  → マージ f497072（2 コミット）
  統合検証 FAIL (exit 1)   ← slugify / wordcount / truncate / index のテストが import エラー
```

**原因**: 統合検証（全テスト）を毎 Wave 後に回していた。Wave 1 の時点では後続 Wave のモジュールが存在しないので当然落ちる。
claude-looper は中間 Wave で `pnpm verify`（lint・typecheck・unit）、Milestone 完了時のみ `verify:full` と分けており、
型チェックは「まだ無いモジュール」を参照しないから通る。テストを真実にする loop-harness では同じ構造が成立しない。

**修正**: 検証を 2 種類に分けた。

- **回帰検証**（毎ラウンド、マージがあれば）: これまでに完了した全タスクの `verify.command` を重複除去して順に実行。
  「マージで既存の完了タスクを壊していないか」だけを見る。Wave に `verify` を書けばそれで置き換え可
- **統合検証**（全 Wave 終了後に 1 回）: `wave.config.json` の `verify.command`（全テスト）。これが最終的な真実

**うまく動いていたこと**（記録しておく価値がある）

- worktree の作成、`loop.mjs --worktree` による targetDir / progressFile の写し、worktree 内での自動コミット（2 コミット）、
  `--no-ff` マージ、worktree とブランチの削除、`wave-summary.json` の出力
- 途中で失敗しても `git worktree list` にゴミが残らなかった

**後始末と手順ミス**: マージ済みの Wave 1 を含むブランチを土台のコミット `083433e` へ `git reset --hard` で戻した。
このとき **まだコミットしていなかった wave.mjs の修正とこのログの追記も一緒に消えた**。修正はコミットしてから reset すべきだった。
内容は手元にあったので再適用したが、「ランナーがブランチを進める設計では、人間側の未コミット変更と混ざる」という
運用上の注意点として残す。wave.mjs が起動時にクリーンな作業ツリーを要求するのは、この事故を防ぐためでもある。

wave ランナーは自分の状態を持たない（git の HEAD が状態）ので、途中から再開すると同じタスクが再度走り、
進捗メモに「反復 1」が二重に付く。**再開機能は今後の課題**として残す

### 試行 2 回目（成功）

検証を分離した版で、土台コミット `083433e` から再実行。

```
Wave 1 契約       : 01-contract complete（3 反復）→ マージ                      回帰 PASS（1 タスク）
Wave 2 モジュール : 02 / 03 / 04 を 3 並列。03 は 1 回目をわざと間違えて 4 反復   回帰 PASS（4 タスク）
                    → 3 つを直列マージ（2 + 3 + 2 コミット）
Wave 3 統合       : 05-index complete（3 反復）→ マージ                         回帰 PASS（5 タスク）
統合検証 PASS（17 テスト）  マージ 5 件  所要 約 15 秒（モック）
```

- `git log` には「loop(<task>): 反復 N …」のコミットが各 worktree から流れ込み、その上に `--no-ff` の
  「wave(textkit/<Wave>): <task> をマージ（N コミット）」が載る。**どの反復で何が起きたかがブランチ履歴だけで追える**
- `git worktree list` と `git branch --list 'loop/*'` は実行後に空。後片付けは正常
- 並列 3 タスクは同じ HEAD から分岐し、互いに別ファイルを書くのでマージは全部 fast-forward 不可の通常マージで衝突なし
- 契約先行が効いている: Wave 2 の 3 タスクは `contract.mjs` を import するが、Wave 1 のマージ後に分岐するので全 worktree に存在する

### 試行 3 回目: 衝突経路のテスト（環境で失敗）

衝突経路（`MOCK_CONFLICT=1`）を試すには textkit が未実装の状態が要る。作業ブランチは実装済みなので、
土台コミットをスクラッチ領域にクローンして回した。すると Wave 1 の worktree 作成で失敗:

```
fatal: '$GIT_DIR' too big
```

**原因**: Windows のパス長制限。worktree を `runs/<wave>/<日時>/wt/<id>` に置いていたため、スクラッチ領域の深いパス
（約 170 文字）＋リポジトリ＋runs 配下で、worktree の `.git` ファイルが指す gitdir のパスが上限を超えた。
作業ブランチでの試行 2 回目はパスが短かったので通っていただけ。

**さらに悪いこと**: worktree 作成失敗を「そのタスクをスキップ」扱いにしていたため、同じ失敗を 3 ラウンド繰り返してから
ラウンド上限で止まった。環境要因の失敗は再試行しても直らない。claude-looper も同じ「スキップして続行」で、
これが評価ノートで指摘した「コミットなし Wave の再実行」と同種の無駄な回転になる。

**修正**

- worktree の置き場を設定可能にし（`worktreeBase` / `--worktree-base`）、既定を OS の一時ディレクトリ配下の短いパスにした。
  claude-looper が `/tmp/ralph-worktrees` を既定にしているのと同じ判断に、遠回りして辿り着いた
- worktree 作成失敗は即停止（`worktree_failed`）。ラウンドで再試行しない

### 試行 4 回目: 衝突経路（成功）

クローン先を短いパス（`%TEMP%\lh-conflict`）にし、textkit を未実装に戻す実験用コミットを置いて `MOCK_CONFLICT=1` で実行。

```
Wave 2 ラウンド 1: 02 マージ / 03 マージ / 04 マージ衝突 → abort
                   → 「textkit-04-truncate の進捗メモを取り込み（コードは未完了のため破棄、ラウンド 1）」を自動コミット
                   回帰検証 PASS（完了済み 3 タスク）
Wave 2 ラウンド 2: 04 を新しい HEAD から再実行 → complete → マージ   回帰検証 PASS（4 タスク）
Wave 3            : 05 マージ → 統合検証 PASS   マージ 5 件
```

- 衝突は `src/CHANGELOG.md` の add/add（03 と 04 が別内容で新規作成）。ラウンド 2 では 03 の版が HEAD にあるので 04 は追記になり、衝突しない
- **記憶だけ残す**方針が機能した。再実行された 04 の worktree では `PROGRESS.md` にラウンド 1 の「反復 1・2」が残った状態で始まる
- ただし再実行側の反復番号が「反復 1」から振り直されるため、メモの中に「反復 1」が 2 回現れる。
  ランナーが試行回数を `loop.mjs` に渡して「試行 2 / 反復 1」と表記するのが次の改善
- `git worktree list` はクリーン、一時ディレクトリの worktree 置き場も空

### 項目 2 のまとめ

| 観点 | 結果 |
|---|---|
| 試行回数 | 4 回（設計ミス 1、環境問題 1、成功 2） |
| 学んだこと | 検証は「回帰（途中）」と「統合（最後）」に分ける / worktree は短いパスに / 環境要因の失敗は再試行しない / ランナーが進める設計では人間の未コミット変更を混ぜない |
| claude-looper との差 | done 判定・マージ・検証がすべてランナー側。未完了タスクは記憶だけ引き継ぐ |

## 3. new-task.mjs の PROMPT 雛形を Planner 形式へ

mazechase と textkit の PROMPT.md がすでに持っている構造（作成するファイル / 型定義・シグネチャ / 仕様 / import 先 /
実装パターン / 注意事項 / やってはいけないこと）を雛形に入れる。claude-looper の planner.md の「Builder が docs/ や
既存コードを読まずに実装できるレベル」をそのまま人手で書くときの型にする。コード変更は雛形文字列だけ。

## 4. fix ループと差し戻し（Verifier の段階的修正権限をランナーで）

### 設計（着手前）

claude-looper の Verifier は「軽微なら自分で直す（3 ファイル以内、最大 3 回）／重ければ fix タスクで Builder に委任」を
**エージェントの判断**で行う。これをランナーの機械的な段階に置き換える。

- **回帰検証をマージごとに行う**（ラウンドの最後に 1 回ではなく）。どのマージが何を壊したかが特定できる
- 回帰 FAIL →
  - **第 1 段 fix ループ**: ランナーが fix タスク（設定・仕様・進捗メモ）を `runs/` 配下に生成し、本体チェックアウト上で
    `loop.mjs` を回す。許可ツールを狭め（Write なし = 新規ファイル不可）、反復 2 回・予算小。検証コマンドは落ちた回帰コマンド。
    通れば `fix(wave/…)` としてランナーがコミット
  - **第 2 段 差し戻し**: fix でも通らなければ、fix の変更を捨て、そのマージだけを `reset --hard HEAD^` で取り消す。
    タスクの進捗メモに「ラウンド R のマージは回帰検証で差し戻し」と失敗出力を追記して保存し、次ラウンドで再実行
  - **第 3 段**: ラウンド上限で停止（既存）
- 統合検証（最終）の FAIL も第 1 段の fix ループを 1 回だけ試す。差し戻し先が無いので、それでも FAIL なら失敗終了
- claude-looper の「3 ファイル以内」の判定は、許可ツールと反復数と予算で代替する。ファイル数の判定より機械的で、超えたら勝手に止まる

**モックの拡張**: `MOCK_BREAK=1` で 04-truncate が自分のテストには影響しない形で契約（`WORD_SEPARATOR`）を壊す。
04 自身の検証は truncate.test.mjs だけに絞る（そうしないと 04 の worktree 内で落ちて回帰まで届かない）。
回帰で 01 の contract.test.mjs が落ち、fix ループのモックが契約を戻す。`MOCK_BREAK=2` では fix のモックが何もせず失敗し、差し戻しの経路に入る。
差し戻し後の再実行では、進捗メモに「差し戻し」の記録があるのを見て契約を壊さない

### 実装と試行（項目 4、いずれも 1 回で成功）

`wave.mjs` を全面的に書き直し（約 480 行）。マージごとの回帰検証、`runFixLoop`（fix タスクの生成と実行）、`tryFix`（再検証で判定）、
差し戻し（`reset --hard HEAD^` + 進捗メモへの失敗出力の追記）を追加。短いパスのクローン 2 つで実行。

**MOCK_BREAK=1（fix で直る）**

```
04-truncate: マージ 9e51146 → 回帰検証 FAIL（4 コマンド、contract.test.mjs が落ちる）
  fix ループ起動（2 反復・$1 まで）→ complete（2 反復）→ 再検証 PASS
  → fix(textkit/モジュール): textkit-04-truncate のマージ後の回帰を修正 … をコミット
Wave 3 → 統合検証 PASS   マージ 5 件  fix 1 回
```

- fix タスクの PROMPT.md には、状況（どの Wave でどのマージの直後か）、完了条件、落ちた検証の出力、方針（`git diff --name-only HEAD^ HEAD` で直近の変更を疑う）が入る
- fix の `loop.mjs` は既定 `--no-commit` で走り、コミットはランナーが再検証してから行う。**fix の完了宣言も信じていない**

**MOCK_BREAK=2（fix が失敗 → 差し戻し）**

```
04-truncate: マージ 29f8ba8 → 回帰検証 FAIL
  fix ループ max_iterations（2 反復）→ 再検証 FAIL
  → マージを取り消し（reset --hard HEAD^）。履歴から 29f8ba8 が消える
  → 「textkit-04-truncate の進捗メモを取り込み（コードは差し戻し、ラウンド 1）」をコミット
Wave 2 ラウンド 2: 04 を再実行。進捗メモに差し戻しの記録があるので契約に触れず → マージ → 回帰 PASS
Wave 3 → 統合検証 PASS   マージ 5 件  fix 1 回
```

- 差し戻されたタスクの進捗メモには「### ランナー: ラウンド 1 のマージは回帰検証で差し戻し」と失敗出力が残り、
  再実行時のエージェント（モック）はそれを読んで行動を変えた。**記憶だけ残す方針が、差し戻しの学習経路として機能する**ことの確認
- 終了後の作業ツリーはクリーン、worktree は本体のみ

### 項目 4 のまとめと claude-looper との対応

| claude-looper（Verifier エージェントの判断） | loop-harness（ランナーの機械処理） |
|---|---|
| 検証失敗の原因を分析し「軽微か設計問題か」を判断 | 判断しない。まず狭い権限・小予算の fix ループを 1 回試す |
| 軽微なら自分で修正（3 ファイル以内、最大 3 回） | 許可ツール（Write なし）と反復数・予算で範囲を機械的に制限 |
| 設計問題なら fix タスクを milestones.json に追加して Builder へ | そのマージだけ取り消し、失敗出力を進捗メモに添えて元タスクを再実行 |
| Verifier が done を付ける | ランナーが再検証して初めて done。fix の自己申告も使わない |

## 6. fix ループと差し戻しを本物で発火させる（2026-09-04）

### 設計

実装済みの textkit の上に「拡張タスク」を載せ、回帰検証を意図的に落とす。2 つの wave を別々に回す。

| wave | タスク | 狙い | 仕組み |
|---|---|---|---|
| `textkit-fix` | 07 truncate を単語境界で切る | fix 成功 | 仕様は「区切りが無い場合」を書いていない。既存の truncate テスト（`'abcdefghij', 5` → `'abcd…'`）が落ちる可能性があり、落ちても分岐を足せば直せる |
| `textkit-revert` | 06 省略記号を `...` に | 差し戻し | 契約テストと truncate テストが `…` を期待するので、テストを変えずには両立しない。fix は失敗して差し戻しになるはず |

**ランナーへの追加**

- `regressionTasks`: この wave の前から完了しているタスクの ID。回帰検証にその検証コマンドを含める。これが無いと
  拡張タスクだけの wave では回帰検証が自分のテストだけになり、既存テストの破壊を統合検証まで検出できない
- `fix.protectedPaths`（既定 `['test']`）: fix ループが保護パスを変更していたら、検証結果にかかわらず fix を無効にする。
  fix エージェントが「テストを弱めて通す」抜け道を塞ぐ。本物のエージェントを相手にするので必要になった

**不確定要素**: 07 のエージェントが `test/truncate.test.mjs` を読んで自主的に区切り無しの分岐を入れると回帰は落ちず、
fix は発火しない。それ自体も観察結果として記録する。

### 結果（textkit-fix と textkit-revert、本物の Claude）

**差し戻しの機構自体は本物でも正しく動いた。**

### 観察 1: fix エージェントが「Verifier の判断」を自分でやった

07 の fix ループ（2 回とも）は **コードを一切変更せず**、次を進捗メモに書いて終了した。

- 落ちた 3 件のうち 2 件（ellipsis テスト）は直近のマージが原因ではなく、マージ前から落ちていた（`git show` で確認）
- 残る 1 件は `truncate-words.test.mjs` と `index.test.mjs` が同じ関数に逆の挙動を要求しており、実装側では両立不能
- 「このループでは修正できないので差し戻しを求める」「解決には test/ の変更かタスク定義の見直しが必要で、fix の権限外」
- ランナーへの改善提案: **「マージ直前の HEAD で回帰テストが PASS していたかを先に確認するとよい」**

06 の fix ループは契約定数を `…` に戻して自分の検証（contract テスト）を通し完了を宣言したが、
ランナーの再検証（全回帰コマンド）で 06 自身の ellipsis テストが落ちて fix は無効化された。
fix エージェント自身も「2 つのテストが同一定数に対する相反アサートで、コード側では解消できない」と書いている。

claude-looper では Verifier エージェントが「軽微か設計問題か」を判断して委任先を決める。loop-harness では判断させず
権限を絞った fix ループを回すだけだが、**本物のエージェントは自分で設計問題だと診断し、手を出さずに人間向けの申し送りを残した**。
権限を絞ることが「診断だけして返す」行動を引き出している。

### 観察 2: 私の実験設計の誤り（fix 成功の経路は観察できていない）

- 07 は「区切りが無い場合の扱い」で既存テストが落ちると想定したが、エージェントは初回から fallback を入れていた。
  代わりに `index.test.mjs` の `summarize(...).title === 'Hello Wonderful Wor…'` が単語境界方式と**論理的に矛盾**していた。
  つまり 07 も 06 と同じ「仕様がテストと矛盾する」実験になっており、fix が成功する余地は最初から無かった
- 06 用に追加した `ellipsis.test.mjs` は `05-index` の検証コマンド（全テスト）に含まれ、マージ前から落ちていた。
  07 の回帰失敗 3 件のうち 2 件はこれで、fix エージェントの時間を無関係な調査に使わせた
- fix エージェントの提案どおり、**ベースライン検証**（マージ前の HEAD で回帰コマンドが通るかを wave 開始時に確認）を追加した。
  これがあれば $0 で実験設計の誤りが検出できていた

### 観察 3: fix ループの検証範囲

06 の fix は「落ちた 1 コマンド（contract テスト）」だけを検証コマンドにしていたため、それだけ通して完了を宣言した。
ランナーの再検証は全回帰コマンドなので食い違い、無効化はされたが fix の 2 反復目（$0.46）は無駄だった。
**fix ループ自身の検証コマンドを再検証と同じ全コマンド（`&&` 連結）に揃えた。**

### 観察 4: コスト

- fix ループは 1 回 $1.0〜2.1。タスク本体（$0.9〜1.3）と同程度かそれ以上。fix の反復 1 だけで 23 ターン $1.24 かかった例がある
  （fix の予算 $1.5 を超えたのは反復後に判定するため）。差し戻し 1 回の総費用は「タスク + fix + 再実行」で約 $3
- 2 つの wave の合計 $10.17、26 分。差し戻し 4 回、マージ 0 件。「仕様が矛盾している」状況では
  ラウンドを重ねても解決しないので、**ラウンド上限は小さく**（2）しておくのが正しかった

### 観察 5: 差し戻し後の再実行

06・07 とも、ラウンド 2 のエージェントは進捗メモの差し戻し記録を読み、矛盾の構造を正確に理解したうえで
