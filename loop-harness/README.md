# loop-harness — ループエンジニアリングのハーネス

## ループエンジニアリングとは

AI に「何を言うか」ではなく、**AI を「どう回すか」を設計する**ことです。

| 呼び名 | 設計対象 | 問い |
|---|---|---|
| プロンプトエンジニアリング | 1 回の指示文 | どう頼めば良い答えが返るか |
| コンテキストエンジニアリング | 1 回に渡す情報 | 何を見せれば正しく判断できるか |
| **ループエンジニアリング** | **反復の構造（ハーネス）** | **失敗しても最終的に正解へ収束する仕組みは何か** |

LLM は 1 回で完璧な成果を出しません。しかし「実行 → 外部で検証 → 結果を見せて再実行」を
繰り返せば、1 回の賢さに頼らずに成果へ到達できます。その**外側の繰り返し構造**を
コードとして設計・チューニングする営みがループエンジニアリングです。
代表例は `while true; do cat PROMPT.md | claude -p; done` という 1 行のシェルループ
（いわゆる Ralph ループ）で、そこに停止条件・記憶・検証・スタック検知を足していったものが
実務で使われるループです。

### ループを構成する 6 要素

1. **新鮮なコンテキスト** — 反復ごとにセッションを作り直す。長い会話で判断が鈍る「コンテキスト腐敗」を防ぐ。
2. **外部検証器が真実** — テスト・型チェック・lint の結果だけを信じる。AI の「できました」は信じない。
3. **反復間の記憶** — 会話履歴ではなく、AI が自分で書く進捗メモ（PROGRESS.md）で引き継ぐ。
4. **停止条件** — 完了・最大回数・予算・スタック・エラー。止まらないループは事故になる。
5. **スタック検知とエスカレーション** — 同じ失敗が続いたら「別の方法で」と圧をかけ、それでも駄目なら人に返す。
6. **可観測性** — 反復ごとのプロンプト・応答・検証結果をすべてログに残す。

「ツール」「タスク定義」「作業対象」「実行ログ」を階層で分けています。

```
loop-harness/

├── bin/
│   ├── loop.mjs            ランナー本体（Node.js、依存なし）
│   ├── wave.mjs            複数タスクを git worktree で並列に回し、ランナーがマージと検証を行う
│   ├── new-task.mjs        タスクの雛形を生成
│   └── reset-example.mjs   例題タスクを初期状態に戻す
├── tasks/                  タスクごとに 1 フォルダ
│   ├── slugify/
│   │   ├── loop.config.json  対象ディレクトリ、検証コマンド、エージェント起動、停止条件
│   │   ├── PROMPT.md         タスク仕様（人間が書く。完了条件を必ず明記）
│   │   └── PROGRESS.md       反復間の記憶（エージェントとランナーが追記）
│   ├── 2048-01-core/       2048 のコアロジック（Opus）
│   ├── 2048-02-cli/        2048 のターミナル UI（Sonnet、01 の成果物に依存）
│   ├── 2048-03..06/        2048 のデスクトップ版（view / Electron 本体 / exe 生成 / 見た目の回帰修正）
│   ├── mazechase-01..04/   迷路追いかけゲーム（迷路と自機 / 敵の移動 / ゲーム進行 / UI）
│   ├── textkit-01..05/     wave.mjs 用: 契約 → 3 モジュール並列 → 統合 の 5 タスク
│   └── textkit/            wave.config.json（Wave の並びと統合検証コマンド）
├── examples/
│   ├── slugify/            エージェントの作業対象（src/ に実装、test/ が検証器）
│   ├── game2048/           2 タスクで作ったターミナル版 2048 と、4 タスクで作った Electron 版（test/helpers/probe.cjs が見た目の検出器）
│   ├── mazechase/          4 タスクで完成させた迷路追いかけゲーム
│   ├── textkit/            wave.mjs で 3 Wave 5 タスクを並列に回して作った小さなテキスト処理ライブラリ
│   ├── mock-agent.mjs      Claude を呼ばない偽エージェント（無料で動作確認用）
│   └── mock-agent-textkit.mjs  textkit 専用の偽エージェント（MOCK_CONFLICT=1 でマージ衝突を再現）
└── runs/<タスク>/<日時>/    反復ごとのログ iter-NN.md と summary.json（git 管理外）
    ├── setup.md            setup.command の実行記録（設定にあるときだけ）
```

設定ファイル内のパスはすべて設定ファイルの場所からの相対パスです。フォルダごと移動やリネームしても動きます。

### 1 反復の流れ

```
（反復 1 の前に 1 回だけ）setup.command で環境準備 → 失敗ならループを始めない
検証コマンド実行 ──→ PASS かつ前回「完了宣言」あり → 完了・停止
   │                 （verify.artifacts があれば、生成された画像などを runs/<日時>/artifacts/iter-NN/ に写す）
   ├─ FAIL が前回と同一 × N 回 → スタック・停止（その前に「別の方法で」と警告）
   │
   └─ 仕様 + 進捗メモ + 検証結果 でプロンプトを組み立て
         → エージェントを 1 回起動（claude -p、stdin でプロンプト、cwd は作業対象。git は禁止）
         → 応答・コスト・完了マーカー・<spec-issue>（仕様への指摘）を記録
         → エラー / 予算超過なら停止、そうでなければ次の反復へ
```

エージェントが完了マーカー `<promise>COMPLETE</promise>` を出しても、**次の反復の検証が PASS しなければ完了扱いにしません**。
逆に検証が PASS していてもマーカーが無ければ、もう 1 回「完了条件を確認せよ」と起動します。
この 2 段構えにより、テストで検出できない完了条件（コメントの有無など）もエージェント自身が確認する機会が生まれます。

完了判定は常にランナーの検証結果で行うので、エージェントには「検証が FAIL の状態で起動されても、直したあと検証コマンドを
自分で実行して PASS し、完了条件をすべて確認したならマーカーを書いてよい」と伝えています。以前は FAIL 起点の反復では
マーカーを禁止していたため、最短でも「実装 → 宣言だけの反復 → 検証で確定」の 3 反復が要りました。2048 デスクトップ版の 4 タスクでは
「宣言だけの反復」が費用の 33%（$1.36 / $4.12）を占めたので、最短経路を「実装（自己検証 + 宣言）→ 検証で確定」の 2 反復にしました。
エージェントの自己検証は「宣言してよいか」の条件に使うだけで、真実はランナーの検証です。

## 使い方

### まず無料で動きを見る（モックエージェント）

```bash
npm run loop:mock
```

モックは意図的に 1 回目で不完全な実装を書き、2 回目で検証出力を読んで直し、検証コマンドを自分で実行して PASS を確認してから
完了を宣言します。3 回目はランナーの検証だけで確定し、エージェントは起動されません（エージェント起動 2 回、反復 3 回）。
`runs/slugify/` に各反復のプロンプトと応答が残るので、ループが何を見て何をしたかを追えます。
`MOCK_SPEC_ISSUE=1 npm run loop:mock` とすると、モックが仕様の抜けを `<spec-issue>` で報告し、ランナーが終了時に列挙する経路も見られます。

もう一度試すときは:

```bash
npm run reset:example
```

### 本物の Claude Code で回す

```bash
npm run reset:example
npm run loop -- --task slugify --max 3 --budget 1
```

`tasks/slugify/loop.config.json` の `agent.args` 既定値は、編集系ツールと `node` コマンドだけを許可した比較的安全な設定です。
`--max-turns 40` で 1 反復あたりのツール呼び出し回数も制限しています。
費用の上限は `loop.maxCostUsd`（既定 $3）、回数上限は `loop.maxIterations`（既定 8）です。
コマンドラインで `--max 3 --budget 1` のように上書きできます。

実測（2026-09-03）: 例題 slugify は 3 反復・約 $0.73・約 1 分 40 秒で完了。反復 2 でエージェントがテストでは検出できない
完了条件（JSDoc の行数）の違反を自分で見つけて修正した。

実測（2026-09-04、宣言の緩和後）: 同じ例題が 2 反復・$0.49・1 分 6 秒で完了（エージェント起動は 1 回、10 ターン）。反復 1 で実装し、
検証コマンドを自分で実行して 4/4 PASS を確認、完了条件 4 つを照合して宣言し、反復 2 のランナーの検証で確定した。
JSDoc の行数も反復 1 の中で仕様に合わせて縮めている。あわせて「非 ASCII 文字の扱いが仕様にもテストにも無い」を
`<spec-issue>` で報告し、ランナーが終了時に列挙した。

### 例題 2: 2048 を 2 タスクに分けて作る

「システム規模のものは機能単位に分割して直列に回す」の実例です。ターミナル版 2048 を、
コアロジック（`tasks/2048-01-core`）と UI（`tasks/2048-02-cli`）の 2 タスクで完成させました。

**進め方**

1. 人間がテストを先に書く。`examples/game2048/test/game.test.mjs`（盤面ロジック 23 ケース）と `test/cli.test.mjs`（描画と非対話モード 7 ケース）
2. `new-task.mjs` で 2 タスクを生成し、仕様を書く。01 は `game.mjs` の純関数だけ、02 は 01 を import して `cli.mjs` を作る
3. 01 を回す。完了後に `cli.test.mjs` を配置し、02 を回す（02 の検証は 01 のテストも含めて回帰させる）

```bash
node bin/loop.mjs --task 2048-01-core
node bin/loop.mjs --task 2048-02-cli
```

**対話 UI を検証可能にする設計**

矢印キー操作そのものは自動検証できません。そこで同じコードに非対話モードを設け、そちらをテストの入口にしました。
`node src/cli.mjs --seed 42 --moves LLUR` のように種と手順を渡すと、対話せずに最終盤面を出力します。
乱数を種付きで注入しているので、テスト側が仕様どおりに手順を再現し、CLI の出力と完全一致を要求できます。
残った「実際にキーで操作できる」だけは検証不能な完了条件として仕様に残し、エージェントが完了宣言前に自分で確認する形にしました。

**実測（2026-09-03）**

| タスク | モデル | 反復 | 費用 | エージェント実行時間 |
|---|---|---|---|---|
| 01 コアロジック | Opus 5 | 3 | $0.77 | 1 分 37 秒 |
| 02 ターミナル UI | Sonnet 5 | 3 | $0.60 | 2 分 21 秒 |

どちらも「反復 1 で実装、反復 2 で完了条件を照合して宣言、反復 3 の検証で確定」の最短経路でした。
事前見積もりは $3.5〜5 で、実際はその 3 分の 1 以下です。テストを先に用意し仕様を細かく書くほど反復数が減る、という関係がそのまま出ています。

遊ぶには:

```bash
node examples/game2048/src/cli.mjs
```

矢印キーで操作、`q` で終了です。

### 例題 2b: 2048 を Windows アプリ（exe）にする

例題 2 のターミナル版を、同じ盤面ロジック（`game.mjs`）のまま Electron のデスクトップアプリにし、
ポータブル exe まで作った例です。「見た目」と「exe 生成」という、テストで検証しにくい領域をどう検証可能にしたかが要点です。

**分割と検証の入口**

| タスク | 中身 | 検証の入口 |
|---|---|---|
| 03 view | ゲーム状態の reducer と、状態 → HTML 文字列の純関数 | `node --test`。HTML を 1 要素 1 行の文字列で完全一致 |
| 04 app | Electron 本体（固定サイズ窓、設定ファイル、ベスト保存、CSS） | 静的チェック + `electron . --smoke --user-data <一時dir>` で実際に窓を開き、タイル数と窓サイズを stdout で報告 |
| 05 build | electron-builder で exe（フォルダ + zip） | `npm run build` → `dist/win-unpacked/2048.exe` を `--smoke` で起動。exe が Electron の署名済みバイナリと同一（SHA-256）であることも確認 |
| 06 style | 見た目の回帰修正（改善ループ） | `test/helpers/probe.cjs` でアプリを非表示ウィンドウに読み込み、**計算済みスタイルと矩形**を照合 |

**実測（2026-09-04、Sonnet 5）**

| タスク | 反復 | 費用 | 備考 |
|---|---|---|---|
| 03 view | 3 | $0.83 | 反復 1 で実装、2 で完了宣言、3 の検証で確定 |
| 04 app | 3 | $1.36 | 反復 1 が 49 ターン（Electron の起動と smoke の作り込み） |
| 05 build | 3 | $0.69 | 反復 1 は artifactName 未設定で FAIL、2 で修正 |
| 06 style | 3 | $1.24 | 症状 2 件（CSS 詳細度の衝突、HUD の隙間）を 1 反復で修正 |
| **合計** | **12** | **$4.12** | |

**分かったこと**

- **構造のテストは見た目を保証しない。** 04 は HTML 構造と窓サイズのテストを全部通したが、スクリーンショットを撮ると 2〜16 のタイルが黒かった。
  `.tile:not(.empty)` の詳細度が `.v2` に勝っていた。これを検出するために、計算済みスタイルを読むプローブ（`test/helpers/probe.cjs`）を用意し、
  改善ループ 06 として回した。人間が「見て気づく → 検出器を書く → ループに直させる」の順で、検出器がテスト資産として残る
- **エージェントは仕様の穴を見つける。** 03 で「won / over のときに `new` クラスを付けるか」を仕様に書き忘れていたが、
  テストの期待値から正しい振る舞いを読み取り、進捗メモに根拠を書いた。仕様はその指摘どおりに直した
- **プロジェクトの許可リストは内側のエージェントにも効く。** `.claude/settings.json` に `git commit` を許可した直後、
  `claude -p` で起動した内側のエージェントが自分でコミットした。ランナーがコミットする設計と衝突するので、
  当初は 2048 のタスク設定に `--disallowedTools "Bash(git:*),PowerShell(git:*)"` を足した。いまは `loop.mjs` が
  `claude` を起動するとき常にこれを付ける（`agent.allowGit: true` で解除）
- **人間とランナーが同時に git を触るとロックで衝突する。** ループ実行中に人間がコミットしたら、ランナーの自動コミットが失敗し、
  ステージ済みの変更が人間の次のコミットに混ざった（あとで分割し直した）。いまはランナーが `index.lock` を検知して数回再試行し、
  それでも駄目ならステージを戻して理由を出す。それでも、ループ実行中はそのリポジトリで git を使わない
- **未署名の exe は Windows 11 の Smart App Control にブロックされる。** 最初はポータブル exe（NSIS の自己展開）で通っていたが、同じ日の夜から
  コード整合性ポリシーがブロックし始めた（イベント 3077）。electron-builder が exe にリソースを書き込むと Electron の署名が壊れる。
  `disableAsarIntegrity: true` で exe を無改変（署名済みのまま）にし、配布形式をフォルダ + zip に変えた。ポータブル形式は未署名の
  ラッパーになるので、コード署名証明書が無い限り使えない。この対処は環境の問題なので人間が行い、テストと仕様に反映した
- ポータブル exe（NSIS のラッパー）は子プロセスの stdout を返さない。exe の検証は「ファイルへの書き出し」も仕様に含めた

この開発で見つかった loop-harness 自体の改善点（確認だけの反復を減らす、内側のエージェントに git を渡さない、など 7 件）は
[docs/research/2026-09-04_game2048-desktop-loop-improvements.md](../docs/research/2026-09-04_game2048-desktop-loop-improvements.md) にまとめ、
同日のうちに 7 件すべてをハーネスに取り込んだ（同ドキュメント末尾の「実装状況」と、以下の各節を参照）。

**ビルドして遊ぶ**（初回の `npm install` は Electron 本体約 120MB をダウンロードする）:

```bash
cd examples/game2048
npm install
npm run build
dist/win-unpacked/2048.exe
```

`dist/` は git 管理外です。配布するときは `dist/2048-win-x64.zip` を渡し、展開したフォルダの `2048.exe` を起動してもらいます。
ビルド不要で試すなら `npm start`。操作・設定ファイル・テストの詳細は [examples/game2048/README.md](examples/game2048/README.md)。

盤面の幅は `%APPDATA%\2048\settings.json` の `size`（既定 600、300〜1200）で変えられます。

### 例題 3: 迷路追いかけゲームを 4 タスクで作る

「餌を全部食べる、敵に捕まらない」リアルタイムの迷路ゲーム（`examples/mazechase`）を 4 タスクで完成させました。
2048 より 1 段大きく、コード 5 ファイル約 600 行、テスト 64 件です。

**タスク分割**

| タスク | 成果物 | 内容 |
|---|---|---|
| 01 迷路と自機 | `maze.mjs`, `rng.mjs` | ASCII 迷路の読み込み、壁判定、自機の移動、餌の取得、種付き乱数 |
| 02 敵の移動 | `ghost.mjs` | 交差点で目標に近づく方向を選ぶ、逆走禁止、追跡・散開・逃走の 3 モード |
| 03 ゲーム進行 | `game.mjs` | `step(state, input, rng)` で 1 ティック進める。衝突、パワー餌、残機、勝敗、モードのタイマー |
| 04 ターミナル UI | `cli.mjs` | 描画、非対話モード、リアルタイム対話モード |

各タスクは前のタスクの成果物を import し、検証コマンドには前のタスクのテストも含めて回帰させます。
テストは 4 本とも人間が先に書き、タスクの完了ごとに次のテストを `test/` に置いて回しました。

**リアルタイム性の扱い**

敵は入力が無くても動くので、対話モードは 125 ミリ秒ごとに `step` を呼んで画面を書き直します。
自動検証は 2048 と同じく非対話モードが入口です。`--seed 42 --inputs "RRRR..DDLL"` のように 1 ティック 1 文字の入力列を渡すと、
テスト側が同じ手順を再現して最終状態の完全一致を要求できます。

**敵の挙動の仕様化**

反復を食う所と見ていた敵の AI は、「候補から逆方向を除く → 逃走中は乱数で選ぶ → それ以外は進んだ先と目標の距離の二乗が最小、同点なら up, left, down, right の順」まで
仕様に書き切り、テストも交差点ごとの選択を 1 手単位で固定しました。結果、02 は 3 反復で終わりました。
書き切れない場合は「壁に入らない」「毎回ちょうど 1 マス動く」のような性質テストで補います（このタスクにも 200 手の性質テストを 1 本入れています）。

**実測（2026-09-03）**

| タスク | モデル | 反復 | 費用 | エージェント実行時間 |
|---|---|---|---|---|
| 01 迷路と自機 | Opus 5 | 3 | $0.98 | 2 分 05 秒 |
| 02 敵の移動 | Opus 5 | 3 | $0.97 | 1 分 57 秒 |
| 03 ゲーム進行 | Opus 5 | 3 | $1.51 | 4 分 12 秒 |
| 04 ターミナル UI | Sonnet 5 | 3 | $1.06 | 8 分 05 秒 |
| 合計 | | 12 | $4.51 | 約 16 分 |

事前見積もりは $6〜10 でした。4 タスクすべてが最短の 3 反復で終わっています。

**仕様に書いていない品質は出てこない**

唯一手を入れたのは既定の迷路です。仕様には「幅 15 以上、敵 2 体以上、餌 50 個以上、左右対称、行き止まりが少ない環状の通路」と書きましたが、
エージェントが作ったのは条件を最小限で満たす「外周を一周するだけのリング」でした。遊びとして成立しないため、人間が 21×13 の迷路を手書きし、
全マス連結・行き止まり 0・左右対称をスクリプトで検証して差し替えました。迷路の「面白さ」は検証に落とせないので、ここは人間の仕事として残ります。

遊ぶには:

```bash
node examples/mazechase/src/cli.mjs
```

`@` が自分、`G` が敵、`o` がパワー餌。矢印キーで移動、`q` で終了です。

### 自分のタスクを追加する

1. 作業対象のプロジェクトに、完了を機械判定するテストを**先に**書く。
2. 雛形を生成する。作業対象パスは絶対パスでも、実行場所からの相対パスでも良い。

   ```bash
   node bin/new-task.mjs my-api ../my-api "npm test && npx tsc --noEmit"
   ```

   Python や Rust なら許可ツールを差し替える。

   ```bash
   node bin/new-task.mjs etl C:\work\etl "pytest -q" --tools "Read,Edit,Write,Glob,Grep,Bash(pytest:*),Bash(python:*)"
   ```

   `tasks/<名前>/` に `loop.config.json`（パスは相対に変換済み）、`PROMPT.md`（穴埋め式の雛形）、`PROGRESS.md`（空）ができる。

   環境準備が要るなら `--setup "npm install"`、検証が画像を吐くなら `--artifacts "shots/*.png"`、Electron アプリなら `--electron`
   （計算済みスタイルを読むプローブと存在チェック付きスモークの雛形を作業対象の `test/` に置き、`npx` / `npm` を許可する）を足す。

   ```bash
   node bin/new-task.mjs my-app ../my-app "node --test \"test/**/*.test.mjs\"" --electron --setup "npm install" --artifacts "shots/*.png"
   ```
3. `tasks/<名前>/PROMPT.md` を書く。**完了条件を検証コマンドで機械的に判定できる形にする**のが最重要。
   検証で判定できない条件は番号付きで残しておくと、エージェントが完了宣言の前に自分で確認する。
   雛形の見出し（作成するファイル / 型定義・シグネチャ / 仕様 / import 先 / 実装パターン / 注意事項）は、
   エージェントが他のドキュメントや既存コードを読まずに実装できる粒度を狙ったもの。export 名とシグネチャをここで確定させると、
   Wave 並列のときに他タスクとの契約になる。
4. `node bin/loop.mjs --task <名前> --verify-only` で検証コマンドが動くことを確認してから、
   `node bin/loop.mjs --task <名前> --max 3 --budget 1` で小さく回す。

タスクが 1 つしかないときは `--task` を省略できます。`node bin/loop.mjs --help` で登録済みタスクを一覧できます。

システム規模のものは 1 ループに載せず、`tasks/01-db-schema/`、`tasks/02-user-api/` のように機能単位へ分割して直列に回します。
各タスクの `targetDir` は同じプロジェクトを指し、前のタスクの成果物が次の前提になります。1 タスクの目安は人間なら半日〜1 日、完了条件は 3〜6 個です。

### 反復ごとに自動コミットする（申し送りをコミット本文に残す）

`loop.config.json` に `"git": { "autoCommit": true }` を書くか、`--commit` を付けて起動すると、
**ランナーが**各反復の後に `targetDir` 配下と `PROGRESS.md` の差分をコミットします。
本文にはその反復の進捗メモのブロック（`### 反復 N`）がそのまま入り、末尾に `Loop-Task` / `Loop-Iteration` /
`Loop-Verify` / `Loop-Cost-Usd` / `Loop-Run` のトレーラーが付きます。

```bash
node bin/loop.mjs --task slugify --commit
git log --format='%h %s'          # loop(slugify): 反復 2 検証 FAIL → エージェント 12 ターン
git log --grep='Loop-Verify: FAIL' # 失敗した反復だけを拾う
```

コミットするのはエージェントではなくランナーです。エージェントに git を触らせると「コミットしたから完了」と
誤認する余地が生まれるため、記録は外側で取ります。反復単位で差分が残るので `runs/*/iter-NN.md` と対応が取れ、
巻き戻しもできます。`targetDir` が git 管理外、または `PROGRESS.md` が別リポジトリにある場合は警告して無効化します。
（この機能は [claude-looper の評価](../docs/research/2026-09-04_claude-looper-evaluation.md) で見た
「コミット本文の申し送り」を、エージェントの手を借りずに実現したものです。）

**内側のエージェントには git を渡しません。** プロジェクトの `.claude/settings.json` の許可リスト（例: `Bash(git commit *)`）は、
`claude -p` で起動した内側のエージェントにも効きます。`--allowedTools` に git を書いていなくても、許可リストの側で通ってしまい、
エージェントが自分でコミットした例がありました（2048 デスクトップ版）。そのため `loop.mjs` は `claude` を起動するとき常に
`--disallowedTools "Bash(git:*),PowerShell(git:*)"` を付けます（設定に `--disallowedTools` が既にあれば、その値に足します）。
どうしても渡したいときだけ `loop.config.json` の `agent.allowGit` を `true` にしてください。起動時に「内側のエージェントの git: 禁止 / 許可」と表示します。

**ループ実行中はそのリポジトリで `git add` / `git commit` をしないでください。** git のロック（`.git/index.lock`）はリポジトリ単位なので、
人間のコミットとランナーの自動コミットが重なるとどちらかが失敗します。ランナーはロックを検知したら 0.7 秒間隔で最大 5 回再試行し、
それでも失敗したときは自分が `git add` した分だけステージを戻して（`git reset -q -- <targetDir> <PROGRESS.md>`）、
`[N] 自動コミット失敗: git commit 失敗: <stderr>（ステージを戻した。差分は作業ツリーに残っている）` と出します。
戻さないと、エージェントの差分が人間の次のコミットに混ざります（実際に起きました）。差分は作業ツリーに残るので、ループ終了後に手でコミットできます。

### ループ前の環境準備（setup.command）

エージェントはネットワークに出られないので、`npm install`（Electron 本体約 120MB）やビルドツールの取得は人間が事前に済ませる必要があります。
これを `loop.config.json` の `setup.command` に書いておくと、**反復 1 の前に 1 回だけ**ランナーが実行し、結果を `runs/<日時>/setup.md` に残します。
失敗したらループを始めずに終了します（`summary.json` の `status` は `setup_failed`）。

```json
"setup": { "command": "npm install", "timeoutSec": 900 }
```

進捗メモにもコミットにも残らなかった「環境の準備」が、設定と実行記録の両方に残るようになります。
ループの途中で環境が変わる件（Smart App Control が未署名 exe をブロックし始めた、など）は検証出力から機械的に見分けられないので、
スタック警告の文面に「原因が環境ならば進捗メモに根拠を書いて終了せよ。環境の問題は人間が直す」を足し、
スタックで停止したときの終了メッセージにも同じ注意を出します。

### 見た目の検証: 成果物の保存とプローブ（verify.artifacts）

構造のテスト（クラス名がある、要素数が合う）は見た目を保証しません。2048 デスクトップ版では、テストを全部通したのに
タイルが墨で塗られていました（CSS の詳細度）。対策は 2 段です。

1. **人間が見る材料を残す。** `verify.artifacts` に検証コマンドが生成する画像などの glob（`targetDir` からの相対）を書くと、
   反復ごとに `runs/<日時>/artifacts/iter-NN/` へコピーします。ループ終了後に反復順に並べて見られます。
   **ループの判定には使いません**（画像の良し悪しを自動で判定しない。判定したければ 2 へ）。

   ```json
   "verify": { "command": "node --test \"test/**/*.test.mjs\"", "artifacts": ["shots/*.png"] }
   ```

2. **数値で照合する検出器を書く。** `examples/game2048/test/helpers/probe.cjs` の方式（非表示ウィンドウで読み込み、
   `getComputedStyle` と `getBoundingClientRect` を JSON で吐く）なら、色・寸法・重なり・はみ出し・スクロールの有無まで
   テストで照合できます。`new-task.mjs --electron` がこの方式の汎用プローブと、存在チェック付きスモークの雛形を作業対象の `test/` に置きます。

仕様を書く側の教訓: UI の仕様は「`.v2` クラスを付ける」ではなく「`.tile.v2` の背景は `rgb(255, 255, 255)`、文字は `rgb(42, 42, 42)`」のように
**計算済みの色と寸法**で書き、テストもそこを見る。

### 仕様への指摘を拾う（spec-issue）

エージェントは仕様の抜けや、仕様とテストの矛盾に気づきます（2048 の 03 で「won / over のときに `new` クラスを付けるか」が
仕様に無いことを見つけ、テストの期待値から正しい振る舞いを読み取った）。進捗メモの中に書かれると見落とすので、
プロンプトのルールに「仕様の抜け・曖昧さ・テストとの矛盾に気づいたら最終メッセージに `<spec-issue>…</spec-issue>` で囲んで書く」を入れ、
ランナーが応答から抜き出して

- `runs/<日時>/iter-NN.md` の「仕様への指摘（spec-issue）」節
- `summary.json` の `specIssues`（`{ iteration, text }` の配列）
- 終了時の標準出力（`[loop] 仕様への指摘 N 件 …` として列挙）

に出します。`wave.mjs` も各タスクと fix ループの `summary.json` から集めて `wave-summary.json` と終了時の出力に列挙します。
本物の実行で差し戻しになった 4 回はすべて「仕様がテストと矛盾」が原因だったので、ここを見てから仕様を直して再実行するのが最短です。

同じ指摘は反復をまたいで、またタスクと fix ループの両方から繰り返されます。終了時の列挙では、本文中の `ファイル:行` の参照を
1 つでも共有する指摘を同じグループにまとめ（`bin/lib/spec-issues.mjs`）、グループごとに「どの loop のどの反復が指摘したか」「参照している場所」
「代表の本文（最も長いもの）」を出します。元の指摘は `summary.json` / `wave-summary.json` の `specIssues` にすべて残り、まとめは `specIssueGroups` に入ります。
textkit-revert の本物の 14 件は 6 グループ（矛盾の本体 9 件が 1 グループ、JSDoc の文言、`test-experiments/` 内の食い違い、など）になりました。

実測（2026-09-04、`textkit-revert` を本物の Claude で再実行。進捗メモは初期化してから）: 結果は以前と同じ `max_rounds`（差し戻し 2 回）だが、
終了時に **仕様への指摘 14 件**（タスク 06 が 6 件、fix ループ 2 本が 4 件ずつ）が列挙され、`wave-summary.json` の `specIssues` と各 loop の `summary.json` の件数が一致した。
内容は「`test/contract.test.mjs:6` と `test-experiments/ellipsis.test.mjs:6` が同じ定数に `'…'` と `'...'` を要求しており、`test/` 変更禁止の下では両立する実装が無い」
「`test/truncate.test.mjs:7` の期待値 `'abcd' + ELLIPSIS` は `max=5` と整合せず、省略記号が 1 文字のときだけ偶然一致していた」
「fix ループの仕様にある『他は現在 PASS』が事実と異なる。検証コマンドが `&&` 連鎖なので先頭で止まり、後続の失敗が見えていない」など、
人間が仕様側で決めるべき点と、ランナーの改善候補（fix ループの検証を各コマンド独立に実行して全部の結果を見せる）が含まれていた。

見えた課題も 2 つある。ラウンド 1 のタスク 06 は自分の検証（実験テストのみ）が通るので契約テストとの矛盾に気づかず、JSDoc の文言の矛盾だけを報告した
（矛盾は fix ループとラウンド 2 で拾われた）。また同じ指摘が反復 1 と 2、タスクと fix ループで繰り返されるので、14 件のうち実質は 5 件程度だった。
この実行から出た 3 つの改善（検証コマンドの独立実行、指摘のまとめ、`<blocked>` での打ち切り）は同日のうちに取り込んだ（以下の 2 節）。

### 検証コマンドを複数にする（verify.command の配列）

`verify.command` は文字列 1 つのほか配列でも書けます。配列なら各コマンドを**独立に**実行し、全部の結果（PASS / FAIL と出力の末尾）を
エージェントに見せます。PASS はすべて exit 0 のときです。

```json
"verify": { "command": ["node --test test/unit/*.test.mjs", "npx tsc --noEmit", "npx eslint src"] }
```

`a && b && c` のように連結すると先頭の失敗で止まり、後続の失敗が見えません。wave ランナーの fix ループはこの連結を使っていたため、
fix の仕様に書いた「落ちているのはこれだけ。他は PASS」が事実と異なることがありました（本物の fix エージェントが指摘）。
いまは回帰検証も fix ループの検証も全コマンドを独立に回し、fix の仕様には「どれが FAIL でどれが PASS か」を 1 本ずつ書きます。

### 「自分では直せない」の申告で止める（blocked）

環境の問題（依存の欠落、権限、ネットワーク）や、テスト同士の矛盾、仕様と変更禁止ファイルの矛盾は、エージェントの権限では直せません。
反復を重ねても同じ結論になるだけなので、プロンプトのルールに「そう判断したらコードを変えずに進捗メモに根拠を書き、最終メッセージに
`<blocked>理由</blocked>` を書いて終了する」を入れ、ランナーはこれを見たら**ループを即停止**して人間に返します
（`summary.json` の `status` は `blocked`、`blocked.reason` に理由）。タグ名は `loop.blockedTag` で変えられます。

wave ランナーの fix ループでも同じで、fix エージェントが「テスト同士が矛盾していて実装側では両立できない」と申告したら fix を打ち切って差し戻します。
textkit-revert の本物の実行では fix ループ 2 本が 2 反復とも同じ診断をして予算上限（$1.5）で止まっていたので、1 反復分（約 $0.8）ずつ浮きます。
差し戻しの進捗メモにも「fix エージェントは『実装側では直せない』と申告」と残ります。モックでは `MOCK_BREAK=2` がこの経路を通ります。

### 未実装のときにスモークを即 FAIL にする（テストの書き方）

Electron を起動するスモークテストは、`app/` が空のまま走ると 1 本ごとにタイムアウト（45 秒）まで待ちます（2048 の 04 は反復 1 の検証に 135 秒）。
起動する前に `app/main.cjs` などの存在を `assert` すれば数秒で FAIL になります（2048 の 3 本のテストで確認: 実装ありは 24 件 4.3 秒、
`app/` 無しは 0.3 秒で全件 FAIL）。ランナー側で「前回と同じ失敗なら検証を省く」ような最適化はしません。検証結果が真実、という原則を崩さないためです。

### 複数タスクを Wave で並列に回す（wave.mjs）

独立したタスクが 3 つ以上あるなら、直列ではなく **Wave** 単位で並列に回せます。
`tasks/<名前>/wave.config.json` に Wave の並びを書きます。各 Wave は既存タスク ID の配列です。

```json
{
  "repoDir": "../../examples/textkit",
  "runsDir": "../../runs/textkit",
  "verify": { "command": "node --test \"test/**/*.test.mjs\"" },
  "waves": [
    { "name": "契約",       "tasks": ["textkit-01-contract"] },
    { "name": "モジュール", "tasks": ["textkit-02-slugify", "textkit-03-wordcount", "textkit-04-truncate"] },
    { "name": "統合",       "tasks": ["textkit-05-index"] }
  ],
  "maxParallel": 4, "maxRounds": 3, "maxCostUsd": 10
}
```

```bash
node bin/wave.mjs --wave textkit --dry-run
node bin/wave.mjs --wave textkit
```

**1 Wave の流れ**（判断はすべてランナー。エージェントは worktree の中で `loop.mjs` として動くだけで、git もマージも知らない）

1. 未完了タスクごとに `git worktree` とブランチ `loop/<id>` を HEAD から作り、`loop.mjs --worktree --commit` を並列起動
2. **完了（検証 PASS + 完了宣言）したタスクだけ** を 1 つずつ現在のブランチへ `--no-ff` マージ。衝突したら abort して未完了扱い
3. マージのたびに **回帰検証**: これまでに完了した全タスクの検証コマンドを累積で、**それぞれ独立に**実行（先頭が落ちても全部回す）。落ちたら次の 2 段階で処理する
   - **第 1 段 fix ループ**: ランナーが fix タスク（仕様・設定・進捗メモ）を `runs/` 配下に生成し、本体チェックアウト上で
     `loop.mjs` を回す。仕様には全コマンドを「現在 FAIL / 現在 PASS」付きで列挙し、落ちた全部の出力を添える。
     許可ツールは Read / Edit / Grep 系だけ（新規ファイル不可）、反復 2 回・予算 $1 が既定（`fix` で変更、`--no-fix` で無効）。
     ランナーがもう一度同じ検証を回して通れば `fix(<wave>): …` としてコミット。fix の自己申告は使わない。
     fix エージェントが `<blocked>` で「実装側では直せない」と申告したら、反復を重ねずに打ち切る
   - **第 2 段 差し戻し**: fix でも通らなければ、そのマージだけを `reset --hard HEAD^` で取り消す。失敗した検証（全部）の出力を
     タスクの `PROGRESS.md` に「ラウンド R のマージは回帰検証で差し戻し」として添えて保存し、次ラウンドで再実行
4. 未完了タスク（未達 / 衝突 / 差し戻し）は worktree の `PROGRESS.md` だけを取り込む（**コードは捨て、記憶だけ残す**）。次ラウンドは新しい HEAD から再実行
5. 未完了が残れば次ラウンド（`maxRounds` まで）、無ければ次の Wave。全 Wave が終わったら **統合検証**（`verify.command`）。
   落ちたら fix ループを 1 回だけ試し、それでも落ちれば失敗終了

停止条件は、全 Wave 完了 / ラウンド上限 / 累計コスト上限 / 統合検証 FAIL / worktree 作成失敗 です。
ログは `runs/<名前>/<日時>/` に、タスクごとの `loop.mjs` のログ、fix ループの一式、`wave-summary.json`、回帰・統合検証の出力が残ります。

これは claude-looper の Verifier エージェントが持つ「軽微なら自分で直す（3 ファイル以内・3 回まで）／重ければ fix タスクで Builder に委任」を、
ランナーの機械的な段階に置き換えたものです。「軽微」の判定はファイル数ではなく、許可ツールと反復数と予算で代替しています。

**契約先行**: Wave 1 で後続が import する定数や interface を定義し、Wave 2 以降を並列にします。
同じファイルを触るタスクは別 Wave にします。同じ Wave に入れると衝突して 1 ラウンド無駄になります。

**worktree の置き場** は既定で OS の一時ディレクトリ配下です（`worktreeBase` / `--worktree-base` で変更可）。
リポジトリ内に置くと Windows でパスが長くなり `fatal: '$GIT_DIR' too big` で失敗します。

**モックで試す**: 作業ブランチの textkit は実装済みなので、土台のコミットを別の場所にクローンして回します。

### チューニングの勘所

- 検証が弱いとループは「テストを通すだけ」に収束する。仕様の「やってはいけないこと」を検証に落とせるなら落とす（例: `git diff --quiet -- test/` で test/ 未変更を確認）。
- 1 反復で「1 つの前進」に絞らせると、失敗の切り分けがしやすい。
- スタック警告（`stuckWarnAfter`）は早めに、停止（`stuckStopAfter`）は少し余裕を持たせると、方針転換の余地が生まれる。
- Windows でエージェントに PowerShell を使わせる場合、`--allowedTools` に `PowerShell(node:*)` のように別途許可が必要（Bash の許可は PowerShell ツールに効かない）。
- プロジェクトの `.claude/settings.json` の許可リストは内側のエージェントにも効く。書き系コマンドを足すときは、内側に渡っても問題ないか考える（git はランナーが常に禁止する）。
- UI の仕様は「クラス名」ではなく「計算済みの色と寸法」で書き、テストもそこを見る。外部プロセスを起動するテストは、起動前に成果物の存在を `assert` する。
- 同じ失敗が続く原因が環境（依存・権限・ネットワーク・外部ツール）にあるなら、ループでは直らない。`setup.command` に手順を残し、人間が直してから再実行する。
- `runs/*/iter-NN.md` を読み返して「エージェントが何を見て判断したか」を確認し、仕様・検証・プロンプト文面を直す。この改善サイクル自体がループエンジニアリングです。
  終了時に列挙される「仕様への指摘」（`<spec-issue>`）はその入口になる。

### 既存の大きなシステムを載せる前のチェックリスト

仕様書があるだけではループは回りません。このハーネスは検証コマンドの結果だけを真実にするので、テストが無ければエージェントの完了申告で 1 反復目に止まります。仕様書 3 点（要件定義・設計・README、約 7,400 行の React/TypeScript アプリ）を「ソース無しから作り切れるか」検討したときの手順を、次回のために残します。

**1. 規模を測る**

- 実装行数・ファイル数、テスト件数、依存ライブラリ、検証に必要な環境（ランタイムだけか、ブラウザやビルドが要るか）を数える。
- このハーネスで成功した例（迷路ゲーム: 600 行、テスト 64 件、4 タスク）と比べて「何倍か」を出す。10 倍を超えるなら 1 ループには載らない。

**2. 検証器の有無と調達方針を決める**

- 既存テストがあるなら再利用が最短。テストが import するパスと関数名がそのまま実装契約になる。ただし既存設計の再実装になる。
- 仕様から新規にテストを書くと純度は高いが、準備コストがテスト件数に比例する。契約設計が甘いと「仕様に書いていない品質は出てこない」問題が全面で出る。
- 折衷: 公開 API の契約を人が決めてテストを書き、既存テストを答え合わせに流用する。

**3. ステップに分割する**

- 1 ステップは成功した例の 1〜2 タスク相当（人間なら半日〜1 日）に収める。設計書にフェーズ分割があればそれを土台にし、さらに切る。
- ユニットテストだけで判定できる層（ドメイン、永続化、入出力）を先に、ブラウザ E2E が必要な層（画面の結線）を後に置く。
- 後続ステップの検証コマンドは前ステップのテストも含めて回帰させる。次ステップのテストは前ステップ完了後に置く。

**4. 上限を規模に合わせる**

| 項目 | 小タスクの既定 | 大きなステップの目安 |
| --- | --- | --- |
| `--max-turns` | 40 | 120 |
| `maxIterations` | 6〜8 | 10 |
| `maxCostUsd` | 3 | 20 |
| `verify.timeoutSec` | 300 | 900（E2E は 1,800） |
| `agent.timeoutSec` | 1,800 | 3,600 |

**5. 環境の前提を整える**

- `--allowedTools` に `npm`、`npx`、`tsc`、`vitest` など実際に使うコマンドを足す。Windows では `PowerShell(...)` の許可も別途要る。
- Windows の実行ポリシーで `npm.ps1` が止まる環境では、事前に `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` を実行するか、PROMPT で `npm.cmd` を使わせる。
- 長い仕様書は PROMPT.md に貼らず、ファイルパスで参照させて必要な章だけ読ませる（600 行の設計書は 1 反復で約 25,000 トークンになる）。
- 作業対象は元のリポジトリと分け、別ディレクトリに再構築する。

**6. 人手に残す受入を先に決める**

- 見え方（テーマ、配色）、操作の手触り（ドラッグ、パン）、体感性能、手動起動確認は自動判定できない。各ステップ末に人が確認する項目として PROMPT.md の番号付き条件に書き、ループの完了条件から外す。
- 費用の目安は 1 ステップ 3〜5 反復、1 反復 $2〜8。20 ステップなら $100〜300 程度、所要は数時間から 1 日。無監視で一発ではなく、ステップ単位で回して区切りごとに人が見る運用が前提。
